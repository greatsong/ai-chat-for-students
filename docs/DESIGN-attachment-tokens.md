## 2. 원인

1. **첨부를 매 턴 다시 보낸다.** `providers/*.js`의 `buildMessages`는 히스토리의 모든 사용자 메시지에 대해 첨부 원본(이미지·PDF base64, 텍스트 전문)을 다시 만든다. 첨부 하나가 이후 평균 11턴 동안 계속 과금된다.
2. **트리밍 기준이 모델의 전체 컨텍스트다.** `trimHistoryByTokens`는 모델 한도(Sonnet 5.5 기준 약 100만 토큰)까지 히스토리를 채운다. 학생 대화에 이렇게 큰 맥락은 필요하지 않다.
3. **이미지를 줄이지 않는다.** 휴대폰 사진을 원본 그대로 올린다. Claude는 긴 변 1,568px로 줄여 계산하므로 토큰 차이는 크지 않지만, 요청 본문·DB 용량이 커지고 5MB를 넘으면 Claude가 400으로 거부해 대화가 막힌다.
4. **PDF를 페이지 이미지와 함께 보낸다.** Claude는 PDF 한 쪽마다 텍스트와 페이지 이미지를 함께 넣어 쪽당 대략 1,500~3,000토큰을 쓴다. 글자 위주 PDF라면 추출한 텍스트만으로 충분하다. OpenAI에는 지금 PDF 내용이 아예 전달되지 않는다.
5. **프롬프트 캐싱을 쓰지 않는다.** 같은 히스토리를 몇 분 간격으로 다시 보내지만 캐시 할인을 받지 않는다.

## 3. 설계

### 3-1. 첨부 수명 정책 (효과가 가장 크다)

- 원본은 **첨부한 턴과 그다음 사용자 턴**까지만 보낸다(최근 첨부 메시지 2개).
- 그보다 오래된 첨부는 짧은 대체 텍스트로 바꾼다.
  - `[첨부: 성적분석.pdf, 12쪽. 원본은 앞선 대화에서 제공됨. 요약: …]`
- 대체 텍스트는 업로드 시점에 만든다.
  - 텍스트·CSV: 앞부분 몇 줄과 행·열 수 (기존 `largeFileSampler`의 형식 감지를 다시 사용).
  - PDF: 추출 텍스트 앞 1,000자와 쪽수.
  - 이미지: 첨부한 턴의 AI 답변 첫 문단을 캡션으로 저장(추가 호출 없음).
- 학생이 "아까 그 사진", "첨부한 파일" 같은 표현을 쓰거나 파일 이름을 언급하면 그 첨부만 원본으로 다시 넣는다.
- 위치: `server/utils/attachmentPolicy.js`(신규)에서 히스토리를 받아 오래된 첨부를 대체 텍스트로 바꾸고, `chat.js`가 `buildMessages` 전에 호출한다. 프로바이더 코드는 바꾸지 않는다.
- 학생 화면: 첨부가 대체 텍스트로 바뀐 턴에 "앞서 올린 파일은 요약만 AI에게 전달합니다" 배너를 기존 `context_trimmed` 배너처럼 보여 준다.

### 3-2. 학생 요청의 입력 상한

- 학생 요청은 입력 상한을 모델 한도 대신 고정값으로 둔다(초기값 60,000토큰, 관리자 설정 `student_input_budget`).
- 상한을 넘으면 기존 트리밍·요약 경로를 그대로 탄다. 교사·관리자는 지금처럼 모델 한도를 쓴다.

### 3-3. 클라이언트 이미지 축소

- 업로드 전에 캔버스로 긴 변 1,568px, JPEG 품질 0.85로 다시 인코딩한다(GIF는 제외).
- 평균 1.3MB인 base64가 수백 KB로 줄어 요청 시간과 DB 용량이 줄고, Claude 5MB 거부로 대화가 막히는 문제도 사라진다.
- 위치: `client/src/lib/imageResize.js`(신규), `chatStore.sendMessage`의 업로드 직전.

### 3-4. PDF 텍스트 우선

- 업로드 시 `pdfjs-dist`로 텍스트를 추출한다. 쪽당 글자 수가 충분하면(예: 200자 이상) 텍스트로 보내고, 스캔본처럼 글자가 거의 없으면 원본을 보낸다.
- OpenAI에도 추출 텍스트가 전달되어 지금 빠져 있는 PDF 지원이 생긴다.
- 학생이 그림·표 모양을 물어야 할 때를 위해 첨부 칩에 "원본으로 보내기" 선택을 둔다.

### 3-5. 프롬프트 캐싱

- Claude: 직전 턴까지의 마지막 블록에 `cache_control`을 붙인다. 5분 안에 이어지는 질문은 캐시 읽기 단가(기본 입력의 10%)로 처리된다. 수업 중 연속 질문이 많아 효과가 크다.
- OpenAI·Gemini: 자동 캐싱이 적용되도록 시스템 프롬프트와 히스토리 앞부분을 바꾸지 않는다(요약 삽입 위치를 맨 뒤로 옮기는 정도만 검토).

### 3-6. 사용량 집계와 안내

- 캐시 읽기 토큰은 일일 한도에 별도로 반영한다(예: 10%만 반영). 반영하지 않으면 학생 화면의 사용량과 실제 비용이 어긋난다.
- 첨부가 있는 대화에서 학생에게 "이 대화는 한 번에 약 N토큰을 씁니다. 새 대화를 시작하면 줄어듭니다"를 보여 준다.

## 4. 기대 효과 (추정)

- 첨부 대화에서 첨부 몫은 답변당 약 41,000토큰(56,006 − 14,992)이다.
- 원본을 12턴 중 2턴만 보내면 첨부 몫의 약 80%가 줄어든다. 9월 이후 기준 약 3,800만 토큰, 전체 입력의 약 45%다.
- 캐싱과 입력 상한은 이 위에 추가로 작동한다. 실제 절감률은 3-1을 배포한 뒤 같은 쿼리로 다시 측정한다.

## 5. 순서와 검증

1. 3-1 첨부 수명 정책과 3-3 이미지 축소 (가장 큰 효과, 프로바이더 변경 없음)
2. 3-5 Claude 캐싱 (요청 형식만 변경)
3. 3-4 PDF 텍스트 우선, 3-2 입력 상한, 3-6 안내

검증 방법은 다음과 같다.

- 단위 테스트: 오래된 첨부가 대체 텍스트로 바뀌는지, 최근 2개는 원본인지, 파일 이름을 언급하면 원본이 되살아나는지 확인한다.
- 운영 측정: 위 1장의 쿼리를 배포 2주 뒤 다시 실행해 첨부 대화의 답변당 입력 토큰을 비교한다.
- 품질 점검: 첨부 후 3턴 이상 이어진 실제 대화 10개를 골라, 대체 텍스트만으로 답변 품질이 떨어지지 않는지 교사가 확인한다.
